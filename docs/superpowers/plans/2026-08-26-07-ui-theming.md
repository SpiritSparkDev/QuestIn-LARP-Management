# Plan: UI Theming (Chronicle & Crest + Everest Registry)

## Context

No formal spec doc exists for this plan. The effective spec is:

1. Two design systems the user supplied as drafts in `web_interface/` (gitignored,
   not present in this worktree — their content is fully inlined below):
   - **Chronicle & Crest** — participant-facing (medieval manuscript aesthetic).
   - **Everest Registry** — admin/check-in-facing (deliberately clean/modern, per
     the user's explicit instruction that the check-in tool must look different
     because "hier wirklich nur die Orga reinschauen wird").
2. Two approved mockup artifacts the controller built and the user signed off on
   ("Das klingt richtig. Setz es um.") mapping those systems onto the app's real
   screens and copy (not the generic placeholder content from the original
   drafts). Their complete CSS is reproduced in each task brief below — treat it
   as the exact system to transcribe and adapt, not a loose reference.

This plan applies those two systems to the app's actual existing pages, styling
only — **no backend changes, no change to any business logic**. The app is a
vanilla-JS/no-build-step stack; stay inside that constraint (plain CSS, Google
Fonts via `<link>`, no bundlers, no new npm packages, no CSS frameworks).

Dev server: `docker compose up -d` from the worktree root, app on
`http://localhost:3000`. Test login: `admin@pakyrion.local` / `0000` (admin
role). Frontend files are bind-mounted into the container, so HTML/CSS edits
apply on a browser reload with no restart needed.

## Global Constraints (apply to every task)

1. **Never remove or rename an `id`, `name`, or `for` attribute that an inline
   `<script type="module">` block reads via `document.getElementById`,
   `document.querySelector(All)`, `form.elements.*`, or `new FormData(form)`.**
   Before touching a file, read its `<script>` block and note every selector it
   depends on. You may add new `class` attributes freely for styling. You may
   add new wrapper elements around existing ones. You must not delete an
   element a script selects, and must not repurpose its `id` for something
   else.
2. **`frontend/js/formFields.js` (`escapeHtml`, `renderField`) is off-limits —
   do not edit it.** It is shared, unit-tested (`tests/unit/formFields.test.js`),
   and used for admin-defined dynamic character-schema fields. Its `renderField`
   emits a **bare, unwrapped** `<label for="field-x">…</label><input id="field-x"
   name="x" …>` (or `<select>`/`<textarea>`) pair per field, concatenated
   directly into a container's `innerHTML` — there is no per-field wrapper
   `<div>`. Any CSS that styles dynamic schema fields (in `#dynamic-fields` in
   `characters.html`, or the equivalent in the admin schema builder) must work
   against that flat `label, input/select/textarea` sibling structure — style
   via the container selector (e.g. `#dynamic-fields label { … }`,
   `#dynamic-fields input, #dynamic-fields select, #dynamic-fields textarea {
   … }`), not via a `.field` wrapper class that doesn't exist there.
3. **Small presentational edits to a page's own inline `<script>` are in scope**
   when needed to add a CSS hook — e.g. wrapping a raw status string in
   `<span class="status-pill status-${status}">${label}</span>` instead of
   bare text. This is not a logic change (the underlying data/behavior is
   untouched) and is expected in several tasks below. Do not touch fetch
   calls, event handlers, or control flow beyond what's specified.
   Real backend status values (verify against `tests/unit/statusMachine.test.js`
   if unsure) are exactly: `registered`, `checked_in`, `checked_out`.
4. **No build step.** Fonts load via a `<link>` tag to
   `fonts.googleapis.com` (already proven fine — no bundler, no CDN JS
   frameworks, no Tailwind).
5. **Verify visually**, not just "it loads": use the Claude Browser tools
   against `http://localhost:3000` for every page you touch — check the
   console for errors, and confirm the page still *works* (submit the login
   form, load the characters list, etc.), not only that it *looks* right.
6. **Don't invent scope.** Where a brief gives you exact markup/CSS, use it
   as-is (adapt only where the real page's script needs differ from what's
   shown). Where a brief asks for a small computed value (e.g. a total count),
   compute it from real data already available in that page's script — never
   hardcode a placeholder number.
